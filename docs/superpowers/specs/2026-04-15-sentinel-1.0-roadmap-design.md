# sentinel 1.0 roadmap design

- status: approved, ready for implementation planning
- last updated: 2026-04-15
- author: joe (via brainstorming session)
- supersedes: nothing (first formal roadmap)
- current version at time of writing: v0.1.0

## 1. goals and non-goals

### product goal (1.0)

sentinel-guard is a runtime defense tool for Claude Code. by 1.0 it ships a three-tier defense pipeline (policy, heuristic, local LLM classifier) with org-scale deployment features, validated against a public attack corpus plus a benign-session corpus, after a 30-day community beta.

### north star

vertical depth on Claude Code, all three tiers battle-tested, org-scale policy deployment. not ecosystem. not multi-agent. not research-grade corpus maintenance.

### what 1.0 claims to users

- protects Claude Code from prompt injection at the tool-call layer
- 100% local, no data ever leaves your machine
- complete audit trail, SIEM-ready
- org deployment via git-distributed policy repos
- validated against published benchmarks: X% detection on PromptPressure, Y% false positive on benign sessions (X and Y are placeholders for launch copy; actual numbers come from the v0.5 `sentinel benchmark` run)

### explicit 1.0 non-goals

1. multi-agent support (Codex, aider, Cursor, OpenHands). 2.0 story. pty proxy stub stays a stub.
2. cloud LLM backends for Tier 3. 1.1 via pluggable trait.
3. signed / cryptographically-enforced policies. 1.1. honor-system locked rules are enough for MVP org threat model.
4. push-triggered policy sync daemon. 1.1. `sentinel sync` as explicit CLI verb ships in 1.0; daemon is additive.
5. dashboards, web UIs, policy authoring tools. 2.0.
6. canary / fleet rollout tooling. 2.0.
7. SubagentStop / session-boundary hooks. 1.1. ring buffer sliding-window is enough; session reports derivable from audit timestamps.
8. public attack corpus maintenance as a research project. ongoing ops, not a 1.0 gate.

## 4. architectural decisions

these are the structural decisions that came out of the design process. every v0.2-v0.5 commit respects them. violating one is a review-blocker.

### AD-1, pluggable Classifier trait from day one

tier 3 defines `trait Classifier: Send + Sync { async fn classify(...) -> ClassificationResult; }` in v0.3. `OllamaClassifier` is the only impl in 1.0. 1.1's `CloudClassifier` is a new struct implementing the same trait, no surgery on the evaluation path.

**constraint on implementers:** don't special-case Ollama in the eval pipeline. all tier 3 integration goes through the trait.

**rationale:** tier 3 classification sees the ring buffer (files accessed, commands run, paths touched). shipping that to a cloud API, even to a trusted provider, is a weird posture for a security tool. "sentinel protects your agent from data exfiltration by exfiltrating your tool call history to OpenAI" writes its own takedown tweet. local-first for 1.0 is airtight security posture. cloud opt-in in 1.1 is for users who consciously trade the guarantee.

### AD-2, honor-system locked rules (crypto deferred)

`locked = true` is enforced at policy-layering compose time. a lower layer attempting to override a locked rule from a higher layer produces a parse error + audit event. a developer with filesystem access to the policy file can technically edit it. that's an audit trail, not a tool failure. crypto signing is 1.1.

**constraint on implementers:** locked enforcement lives in the layering code path, not in the eval code path. eval sees the composed effective policy. errors at compose time fail the sync and keep the previous policy active.

### AD-3, `sentinel sync` as explicit CLI verb, daemon-mode-ready

1.0 ships `sentinel sync` as a one-shot command. 1.1 adds a daemon that listens for webhooks and calls the same sync codepath. daemon is additive, not a rewrite.

**constraint on implementers:** factor sync logic so the CLI entrypoint is thin. core sync is a library function that takes config + callbacks. 1.1's daemon reuses it.

### AD-4, PostToolUse logs metadata, not content, by default

schema: `{tool_name, status, exit_code, output_bytes, preview?}`. preview only populated when the matching policy rule sets `capture_preview = true`. preview is length-capped (default 256 bytes) and passes through the redaction pass that already strips secret patterns.

**constraint on implementers:** audit sinks never see raw tool output unless `capture_preview` is opt-in per rule. default config = zero sensitive data in the audit log.

### AD-5, no ambient network calls in default install

CI gets a lint/test that greps the binary for outbound network call sites (`reqwest::`, `hyper::`, `tokio::net::`) and fails if any exist outside opt-in paths (Ollama, git-sync, audit sinks).

**constraint on implementers:** no "check for updates" features. no Sentry/crash reports. no remote schema resolution. if it phones home by default, it doesn't ship.

### AD-6, tier 3 fail-open with single-warning degradation

when Ollama is unreachable, model unpulled, or eval times out: tier 3 skips, one warning per session to stderr + audit log, `sentinel status` reports "tier 3: unavailable (reason)". tiers 1+2 continue unchanged.

**constraint on implementers:** tier 3 errors must never propagate up to block the eval pipeline. eval path is `tier1 -> tier2 -> tier3_or_skip`, never `tier1 -> tier2 -> tier3_might_error`.

### AD-7, audit sinks are symmetric via a trait

`trait AuditSink { async fn write(&self, event: &AuditEvent) -> Result<()>; }`. file, syslog, webhook all implement it. sinks are composable. multiple sinks can be active simultaneously (file + syslog is a common org setup).

**constraint on implementers:** no sink-specific code outside each sink's module. audit dispatcher just iterates configured sinks. failures in one sink don't block others; each sink handles its own retry/buffering.

### AD-8, policy layering precedence with `locked` breaking upward

effective policy is composed by merging layers in order: vendor < org < team < project. higher layers override lower unless the lower layer has `locked = true` on a specific rule. `locked` at a higher layer is a no-op (higher layer already wins by precedence order).

**constraint on implementers:** layering semantics are tested with property tests covering the full lattice (empty layer, locked in each position, conflict resolution). this is the single most bug-prone piece in v0.4. treat it like a protocol, not a config merge.

### AD-9, file-backed ring buffer for tier 2 context

the context window is persisted to disk (bincode or JSON), not held in a background daemon. each `sentinel evaluate` call reads + updates the file. 1.1 may add daemon mode if profiling shows per-call I/O is a bottleneck.

**constraint on implementers:** no background process for state management in 1.0. the ring buffer file is the source of truth. handle concurrent writes gracefully via file lock or atomic swap.

### AD-10, eval path timeout with fail-open

the entire `sentinel evaluate` call has a top-level timeout (default 5s, configurable). if any tier or the full pipeline exceeds it, eval returns `allow` + warning audit event with timeout reason. a blocked agent is worse than a temporarily undefended agent.

**constraint on implementers:** timeout wraps the full tier 1 -> 2 -> 3 pipeline, not just individual tiers. timeout fires -> immediate allow -> audit event with timeout reason.

## 5. quality gate + beta program

### beta cohort recruitment

- **target size:** 5-10 orgs. more if they arrive organically; 5 is the floor for statistical signal.
- **recruitment window:** opens at v0.5 work start (project week 9). earlier than v0.5 ship since lead time > build time. closes at v0.9.0 cut.
- **who counts:** any team or company with ≥2 devs using Claude Code daily. solo indie devs welcome but don't count toward the 5-org floor.
- **channels:** tweet from `@stresstestor`, README beta-signup callout, direct outreach to 15-20 known Claude Code power users.
- **intake:** `docs/beta-signup.md` + GitHub Issues template. captures org name, usage pattern, willingness to share anonymized sessions for benign corpus, preferred contact.

### recruitment fallback tree

| orgs signed by week 10 | action |
|---|---|
| 5+ | ship v0.9.0 on schedule |
| 3-4 | ship v0.9.0, extend beta to 45 days to compensate for thinner signal |
| 0-2 | delay v0.9.0 by 2 weeks, aggressive outreach, reassess at week 12 |

below 3 orgs is back to "dogfooding + vibes," which isn't the 1.0 bar.

### beta commitments (both sides)

| joe commits to | orgs commit to |
|---|---|
| respond to P0/P1 issues within 24h | install sentinel in audit mode for full 30 days |
| respond to P2/P3 within 5 business days | report any false positive / false negative they notice |
| private Slack/Signal channel for urgent reports | file issues in GH Issues, general feedback in GH Discussions |
| weekly status post in Discussions | answer a brief end-of-beta survey (3 questions) |
| public credit in 1.0 launch post (opt-out available) | optionally contribute anonymized sessions to benign corpus |

### severity levels

lives in `docs/severity-levels.md`, shipped before v0.9.0 opens.

| level | definition | example |
|---|---|---|
| P0 | security bypass, data loss, crash on common path | injection sequence bypasses all three tiers; audit log drops events |
| P1 | significant functionality broken, no workaround | policy layering applies wrong precedence; sync fails silently |
| P2 | functionality broken with workaround, polish issues | webhook sink retries forever instead of backing off |
| P3 | minor, cosmetic, docs | typo in error message |

reclassification requires documented justification. this matters because the quiet-period gate depends on consistent classification.

### triage SLA

- P0/P1: response within 24 calendar hours (response ≠ fix; "i've seen it, here's my read" counts)
- P2/P3: response within 5 business days
- P2/P3 can defer to 1.1 with documented rationale; P0/P1 cannot

### quiet-period gate

the 7-day quiet period can begin anytime during beta. the earliest possible 1.0 is day 37 of beta (30-day minimum + 7 quiet). mechanics:

- **clock runs forward** from the most recent P0/P1 close date
- **any new P0/P1 resets the clock to zero**. binary. no partial credit.
- **no upper bound.** if P0s keep landing at day 60, beta keeps running.
- **gate check happens in public** via the weekly Discussions thread. transparency keeps the gate honest.

### continuous benign corpus collection

runs from project week 1, not week 9. every Claude Code session joe runs during the build phase gets logged (raw, pre-anonymization). the artifact-building and anonymization tool (`sentinel export-session --anonymize`) lands in v0.5. by project week 9 the raw corpus is already 50+ sessions without dedicated collection sprints.

this is free data. the raw logs are `sentinel evaluate` events joe is already generating during dogfooding.

### launch content pipeline

- drafts written during v0.5, reviewed during beta, published at 1.0 cut
- artifacts: (1) launch blog post, (2) tweet thread, (3) README 1.0 refresh, (4) GitHub Pages site 1.0 refresh, (5) HN post draft
- transparency notes: benchmark methodology explicitly marked self-validated. external audit called out as a 1.1+ investment. no hype claims the data doesn't support.
- launch-day checklist lives in `docs/launch/checklist.md`

### post-GA rollback plan

- if a P0 lands within 7 days of 1.0 GA: `cargo yank` the version, ship 1.0.1 with fix, post-mortem in Discussions
- if the P0 is a security bypass (not a functionality bug): coordinate disclosure with beta orgs first, then public
- security issues have a private reporting channel: `security@` email alias or GH Security Advisories. documented in `SECURITY.md`.

## 6. explicit out-of-scope buckets

every item here has a home. scope creep into 1.0 from this list is a review-blocker.

### 1.1 bucket (ships within 3-6 months of GA)

| item | rationale |
|---|---|
| signed / cryptographically-enforced policies | honor-system sufficient for MVP org threat model; crypto adds key mgmt, rotation, chain-of-trust complexity. (AD-2 escape hatch) |
| cloud LLM backends (OpenAI, Anthropic, Groq) | violates "100% local" claim in 1.0; trait is pluggable so 1.1 is additive. (AD-1 escape hatch) |
| `sentinel sync` daemon / webhook-triggered pull | sync CLI ships 1.0; daemon reuses same codepath. (AD-3 escape hatch) |
| `sentinel install --enable-scheduled-sync` | cross-platform yak-shaving (cron, launchd); manual cron documented in 1.0 |
| entropy scoring for tier 2 | evaluated during beta; implemented only if data shows tier 2 missing obfuscation-class attacks |
| daemon-backed ring buffer | file-backed is AD-9 default; upgrade only if profiling shows per-call I/O bottleneck |
| `capture_preview = true` flag | ships in 1.0 **unless** v0.4 tripwire fires; otherwise 1.1 |
| SubagentStop / session-boundary hooks | ring buffer sliding-window sufficient; session reports derivable from timestamps |
| `sentinel policy rollback` / `sentinel policy history` | explicit rollback UX for orgs who want guardrails on the guardrails; git revert + sync is the implicit 1.0 path |
| external security audit (Trail of Bits, NCC, etc.) | $15-40k investment; waits for revenue/funding justification |

### 2.0 bucket (post-1.0 maturity)

| item | rationale |
|---|---|
| multi-agent support (Codex, aider, Cursor, OpenHands) via pty proxy | 2.0 is when vertical is proven; pty proxy stub stays a stub in 1.0 |
| dashboard / fleet reporting | needs multiple customer orgs to justify; premature without traction |
| policy authoring web UI | requires web stack + hosting; CLI + TOML sufficient for 1.0 |
| canary / fleet rollout tooling | solves problems only orgs with ≥100 devs have |
| policy marketplace / community sharing | network-effect product; needs users first |
| bug bounty program | ongoing financial + triage commitment; maturity requirement |
| public attack corpus as maintained research project | 1.0 integrates PromptPressure; maintaining an evolving public corpus is 2.0 ecosystem work |
| Windows support | cross-platform is a massive sub-project (path handling, config locations, no launchd/cron equivalent, no UDS); defer until demand signal from 1.0 users |

### never bucket (explicit anti-goals)

| item | why never |
|---|---|
| telemetry / crash reporting in default install | AD-5. "100% local" is the product. any phone-home breaks it permanently. |
| auto-update checks | AD-5. same reason. |
| remote policy schema validation | AD-5. schemas ship with the binary. |
| fail-closed on unknown tool types | catastrophic failure mode for a security tool. unknown tools get pass-through + warning (AD-10 philosophy). |
| running sentinel with sudo/root by default | tool operates in userland; escalation is a sysadmin choice, never a default |
| model fine-tuning / training on user data | even local. "your data trains your classifier" is a liability story. ship the model, don't train it. |
